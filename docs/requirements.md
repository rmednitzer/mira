# Requirements and verification matrix

Implemented status means code and stated checks exist; it does not imply production assurance. Primary CI targets are native Ubuntu 26.04 amd64/arm64. See [validation](testing.md) for commands and exact boundaries.

| ID | Requirement | Acceptance / verification | Status |
|---|---|---|---|
| OPS-01 | Host observation is read-only | Fixed procfs/dpkg reads, an explicitly named fixed-argv systemctl query and fixed-argv journalctl queries; no elevation or mutation | Implemented; representative fleet and isolation assurance pending |
| OPS-02 | Evidence is bounded and parsed | Byte limits, strict supported-field parsing, package status validation, subprocess execution/EOF deadlines, unavailable-state regressions | Implemented for admitted sources; not a universal bound on arbitrary filesystem I/O or descendant lifetime |
| OPS-03 | Evidence cites source, scope and uncertainty | Typed evidence and JSON Lines v1 identify logical sources, recording times and unavailable results | Implemented; record clock trust stays unverified and record freshness unknown. Signer identity is available through signatures ([ADR 0011](adr/0011-host-identity-and-capture-integrity.md)), capture timing and same-boot ordering through [ADR 0010](adr/0010-capture-timeline-and-freshness.md), and a capture age bound through consumer challenges ([ADR 0014](adr/0014-consumer-challenge-freshness.md)); hardware-bound host identity is not established |
| OPS-04 | Read-only investigation template | Explicit service-active, memory-headroom, pressure-ceiling, package-installed, uptime-minimum, kernel-release and journal-events expectations, preserved evidence references, three outcomes, rejected scope and independent contract tests | Seven templates implemented (activation, memory minimum, pressure ceiling, package presence, uptime minimum, kernel release, journal events); broader diagnosis remains planned |
| OPS-05 | Serialized evidence has an independent contract | JSON Schema v1, valid/invalid fixtures and actual CLI output validation | Implemented with separate Python/jsonschema tooling |
| OPS-06 | Capture comparison preserves unknowns | Descriptor-validated bounded input, strict JSON, exact capture source coverage, source/scope matching and explicit indeterminate/missing outcomes | Optional offline Python utility implemented, including comparison-v3 same-boot ordering for timeline captures, signature verification and per-side challenge age bounds; no managed persistent store |
| OPS-07 | Assessment does not become unsupported health or authority | Source-bound observation, fixed reason, unknown states preserved, application health/root cause unassessed | service-active/v1, service-active/v2, memory-headroom/v1, pressure-ceiling/v1, package-installed/v1, uptime-minimum/v1, kernel-release/v1 and journal-events/v1 criteria, native failure and independent schema/semantic tests |
| OPS-08 | Capture completion is separate from availability | Closed profiles, exact source sets, per-source timing/reasons, independent schema/semantic and authored availability tests | Capture-v1/v2/v3 with evidence-v2 records; scope is operator-asserted, not authenticated |
| OPS-09 | Capture timing bounds intra-capture skew and reports same-boot order | One monotonic window per capture, wall-clock consistency within it, opt-in boot binding, comparator order only for matching reported boot IDs; age at consumption stays unanswered without trusted time | Implemented ([ADR 0010](adr/0010-capture-timeline-and-freshness.md)): capture-v2 timeline, opt-in `--bind-boot` and comparison-v3 same-boot ordering with an optional window policy. Live checks on the controlled runner only. Age at consumption: [ADR 0014](adr/0014-consumer-challenge-freshness.md) is implemented (consumer challenge, signed capture-v3, an age bound on the verifier's clock in `mira verify` and the comparator, and a live validator group) |
| OPS-10 | Journal evidence is bounded, text-free and visibility-checked | Closed event classes by catalog `MESSAGE_ID`, current or previous retained boot, fixed text-free `journalctl` argv (sentinel included), running boot selected by bare `--boot`, each `MESSAGE_ID` bound to its actual producer's journald-set `_UID`/`_EXE`/`_SYSTEMD_UNIT`, `coredump` absence assessed only for the current boot with systemd-coredump as its crash handler, counts/unit names/boot-relative times only, a PID 1 visibility sentinel and an all-system-journal-files-openable check before any "none recorded" outcome | Implemented ([ADR 0012](adr/0012-bounded-journal-events.md), [guide](journal-investigation.md)): fixed-argv fixture tests for every outcome and refusal, an independent schema/semantic validator, and a live comparison with direct `journalctl` on the native runners |
| OPS-11 | Representative hosts are qualified with explicit gaps | An unprivileged runner executes the existing independent validators against a chosen binary, classifies each as passed / failed / not applicable with fixed reasons, and writes a closed-field, host-identifier-free receipt; the Phase 1 exit needs one reviewed receipt per required host class, including a restricted-user run | Runner, shared validator contract and receipt schema implemented ([ADR 0013](adr/0013-host-qualification-protocol.md), [guide](qualification.md)) with runner, contract and receipt tests; CI keeps `ci-runner` receipts. Reviewed receipts from the required host classes are outstanding |
| SEC-01 | No proposal grants itself authority | Authenticated principal and independent scoped authorization gate before any action | Not satisfied by retained simulation; operational writes absent |
| SEC-02 | No silent external inference | Offline CLI does not invoke model/network adapters | No such adapters implemented; not an OS-level network-isolation proof |
| SEC-03 | Vulnerability applicability is evidence-bound | Distribution advisory/backport and installed revision evidence required; unknown remains explicit | Planned; package metadata alone is not an exposure finding. package-installed/v1 reports presence only and marks `vulnerability_exposure` not_assessed |
| SEC-04 | UI cannot add capabilities | Only registered components/actions can render and execute | Planned; no adaptive UI exists |
| SEC-05 | Captures and investigation reports can be checked for integrity and signer identity | `mira` signs its JSON output with detached OpenSSH SSHSIG signatures (one namespace per document kind) and verifies them against an operator `allowed_signers` file and one explicit principal; the comparator verifies captures independently; any failure refuses output or comparison; no claim of truthful measurement or freshness | Implemented ([ADR 0011](adr/0011-host-identity-and-capture-integrity.md), [guide](signatures.md)): `--signature`/`--sign-with` on capture and investigate JSON, `mira verify`, and comparator verification bound to the compared bytes. Tested against the real `ssh-keygen`, a fixed-argv fixture and a swap-after-verify race |
| INT-01 | Intent selects declared workflows | Unknown templates/invalid scopes cannot dispatch collection | Closed explicit selection of the seven templates implemented; natural-language intent remains planned |
| MI-01 | Operator and agent share one verifiable record | Signed, append-only session written only by operator-side processes; each entry names its principal (operator, agent or collector, bound to keys by the operator's `allowed_signers`) and the entries it rests on; roles from the operator-signed header only; only collector-signed results count as evidence; gap and cross-session replay detection, and truncation detection against an external close receipt | Stage 1 implemented ([ADR 0015](adr/0015-shared-mixed-initiative-workspace.md), [guide](sessions.md)): canonical signed entries, roles from the header, atomic records, directives, close receipt, agent requests relayed by the broker, collector-signed results and documents, findings, proposals and decisions, and `verify` over all of it |
| MI-02 | Agent autonomy is explicit, per function, bounded and revocable | Manual/advisory/assisted/delegated levels set by operator directives; budget and expiry; operator `stop` precedence; decisions are operator-only; checked on every agent entry | Implemented: the directive state machine (stage 1a), enforced on every agent request by the broker and on every relayed entry by the state rules (stage 1b); operator-only decisions on proposals and findings, with stale approvals refused unless explicit (stage 1c). The operator-clock delegation deadline is not implemented |
| MI-03 | The agent cannot exceed MIRA's closed read-only capabilities | Agent requests run only through an operator-run broker; the action set is exactly the signable captures and templates with existing argument checks; operator-only `--bind-boot`; no shell, file, network or state change; a separate agent OS user is required for model agents; hostile-content fixtures cannot widen it | Broker, capability table, option-injection refusal and `separate_user` layout implemented (stage 1b); hostile model-content fixtures are stage 2 |
| MI-04 | Findings are grounded and reliance is calibrated | Closed claim vocabulary; checkable claims verified against cited results and refused if unsupported; inferences labelled with confidence; optional own-assessment forcing | Implemented except forcing (stage 1c): claims checked against collector results and recorded assessment reasons by the broker, the state rules and an independent validator; hypotheses need a confidence label; `show` labels checked, inference and stale. Reliance itself is measured in stage 3; see [research basis](research/mixed-initiative.md) |
| MI-05 | The model stays outside the trust core | `mira` makes no model call and opens no socket; the agent connects only through a stdio MCP adapter whose tool definitions are fixed and hashed into the session, in a client with no other tools or servers; real sessions use local models; hosted models see synthetic/public sessions only; model I/O recorded | Implemented in part (stage 2, [agent harness](../agent/README.md)): `mira` still makes no model call; the stdio adapter's four tools, pinned by hash in the header and re-checked before every turn; a client host that refuses other MCP servers and non-loopback models, and records every model exchange. Hostile host-content fixtures are outstanding |
| MI-06 | Mixed-initiative benefit is measured, not assumed | Matched tasks against an operator-only baseline: correctness, time, evidence access, over-reliance on seeded wrong findings, override rate | Planned (ADR 0015 stage 3) |
| UI-01 | Task-oriented views improve evidence access | Matched task evaluation against a fixed interface | Research hypothesis |
| EVA-01 | Synthetic experiments are reproducible | Typed inputs and deterministic in-process replay | Retained fixture implemented; no authenticated authorization guarantee |
| TST-01 | Rust subprocess regressions are native | Cargo-built opt-in fixture tests the public CLI without Python or shell | Implemented under test-support; default core suite remains independent |
| TST-02 | Live procfs values agree with surrounding direct observations | Unprivileged kernel/total-memory endpoint agreement, whole-uptime interval, mismatch/unavailable/inconclusive regressions; both native CI architectures | Controlled runner checks implemented and reused by the qualification runner (OPS-11); dynamic values and authenticity remain separate |
| PKG-01 | CLI package has bounded installation scope | Inspect contents, permissions, metadata, checksums, isolated lifecycle and lintian; reject helper/unit/maintainer scripts | Experimental packaging implemented; disposable-container dependency resolution added; physical-host and genuine upgrade tests outstanding |
| PKG-02 | Build artifacts are repeatable under declared variations | Same-binary assembly and two fresh source/target builds compare binaries and complete archives with selected artifacts | Native CI gates and source-bound receipts; shared compiler/system environment, no independent-host or hermetic proof |
| PLT-01 | Platform reads preserve explicit identity and scope | Explicit endpoint/namespace/node, source versions, bounded collection and unknown/partial results; versioned source/profile contracts | Planned only; no Kubernetes or Talos adapter |
| PLT-02 | Platform credentials cannot expand read authority | Scoped permission manifest, verified TLS, explicit credential selection, no executable auth configuration or privileged fallback; exact-request and disclosure tests | Admission gate; not implemented |
| PLT-03 | Integrations preserve offline operation and data custody | Disabled/failing adapter leaves local CLI usable; no mandatory ecosystem tools or hosted control plane; deployment sovereignty and exit review | Planned; see [integration plan](platform-integrations.md) |
| REL-01 | Operational changes verify and recover | Approved writes verify preconditions/postconditions and provide rollback | Deferred; no operational write adapter in MVP |

Release gates also include exact-head Codex review and resolved discussions, required native CI/CodeQL, synchronized source/docs and post-merge identity/CI verification. Signed provenance, physical-host qualification and version-to-version package lifecycle remain additional gates before stable distribution.
