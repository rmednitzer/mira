# Requirements and verification matrix

Implemented status means code and stated checks exist; it does not imply production assurance. Primary CI targets are native Ubuntu 26.04 amd64/arm64. See [validation](testing.md) for commands and exact boundaries.

| ID | Requirement | Acceptance / verification | Status |
|---|---|---|---|
| OPS-01 | Host observation is read-only | Fixed procfs/dpkg reads and an explicitly named, fixed-argv systemctl query; no elevation or mutation | Implemented; representative fleet and isolation assurance pending |
| OPS-02 | Evidence is bounded and parsed | Byte limits, strict supported-field parsing, package status validation, service execution/EOF deadline, unavailable-state regressions | Implemented for admitted sources; not a universal bound on arbitrary filesystem I/O or descendant lifetime |
| OPS-03 | Evidence cites source, scope and uncertainty | Typed evidence and JSON Lines v1 identify logical sources, recording times and unavailable results | Implemented; clock trust unverified, freshness unknown, host identity unauthenticated (signer identity designed in [ADR 0011](adr/0011-host-identity-and-capture-integrity.md)). Capture timeline and same-boot ordering accepted in [ADR 0010](adr/0010-capture-timeline-and-freshness.md) |
| OPS-04 | Read-only investigation template | Explicit service-active, memory-headroom, pressure-ceiling, package-installed, uptime-minimum and kernel-release expectations, preserved evidence references, three outcomes, rejected scope and independent contract tests | Activation, explicit memory-minimum, pressure-ceiling, package-installed, uptime-minimum and kernel-release templates implemented; broader diagnosis remains planned |
| OPS-05 | Serialized evidence has an independent contract | JSON Schema v1, valid/invalid fixtures and actual CLI output validation | Implemented with separate Python/jsonschema tooling |
| OPS-06 | Capture comparison preserves unknowns | Descriptor-validated bounded input, strict JSON, exact capture source coverage, source/scope matching and explicit indeterminate/missing outcomes | Optional offline Python utility implemented, including comparison-v3 same-boot ordering for timeline captures; no managed persistent store |
| OPS-09 | Capture timing bounds intra-capture skew and reports same-boot order | One monotonic window per capture, wall-clock consistency within it, opt-in boot binding, comparator order only for matching reported boot IDs; age at consumption stays unanswered without trusted time | Implemented ([ADR 0010](adr/0010-capture-timeline-and-freshness.md)): capture-v2 timeline, opt-in `--bind-boot` and comparison-v3 same-boot ordering with an optional window policy. Live checks on the controlled runner only; trusted time and signatures remain separate |
| SEC-05 | Captures and investigation reports can be checked for integrity and signer identity | `mira` signs its JSON output with detached OpenSSH SSHSIG signatures (one namespace per document kind) and verifies them against an operator `allowed_signers` file and one explicit principal; the comparator verifies captures independently; any failure refuses output or comparison; no claim of truthful measurement or freshness | Design accepted in [ADR 0011](adr/0011-host-identity-and-capture-integrity.md); not implemented |
| OPS-08 | Capture completion is separate from availability | Closed profiles, exact source sets, per-source timing/reasons, independent schema/semantic and authored availability tests | Capture-v1/evidence-v2; scope is operator-asserted, not authenticated |
| SEC-01 | No proposal grants itself authority | Authenticated principal and independent scoped authorization gate before any action | Not satisfied by retained simulation; operational writes absent |
| SEC-02 | No silent external inference | Offline CLI does not invoke model/network adapters | No such adapters implemented; not an OS-level network-isolation proof |
| SEC-03 | Vulnerability applicability is evidence-bound | Distribution advisory/backport and installed revision evidence required; unknown remains explicit | Planned; package metadata alone is not an exposure finding. package-installed/v1 reports presence only and marks `vulnerability_exposure` not_assessed |
| SEC-04 | UI cannot add capabilities | Only registered components/actions can render and execute | Planned; no adaptive UI exists |
| INT-01 | Intent selects declared workflows | Unknown templates/invalid scopes cannot dispatch collection | Closed explicit service-active, memory-headroom, pressure-ceiling, package-installed, uptime-minimum and kernel-release selection implemented; natural-language intent remains planned |
| OPS-07 | Assessment does not become unsupported health or authority | Source-bound observation, fixed reason, unknown states preserved, application health/root cause unassessed | service-active/v1, service-active/v2, memory-headroom/v1, pressure-ceiling/v1, package-installed/v1, uptime-minimum/v1 and kernel-release/v1 criteria, native failure and independent schema/semantic tests |
| UI-01 | Task-oriented views improve evidence access | Matched task evaluation against a fixed interface | Research hypothesis |
| EVA-01 | Synthetic experiments are reproducible | Typed inputs and deterministic in-process replay | Retained fixture implemented; no authenticated authorization guarantee |
| TST-01 | Rust subprocess regressions are native | Cargo-built opt-in fixture tests the public CLI without Python or shell | Implemented under test-support; default core suite remains independent |
| TST-02 | Live procfs values agree with surrounding direct observations | Unprivileged kernel/total-memory endpoint agreement, whole-uptime interval, mismatch/unavailable/inconclusive regressions; both native CI architectures | Controlled runner checks implemented; dynamic values, authenticity and representative host qualification remain separate |
| PKG-01 | CLI package has bounded installation scope | Inspect contents, permissions, metadata, checksums, isolated lifecycle and lintian; reject helper/unit/maintainer scripts | Experimental packaging implemented; disposable-container dependency resolution added; physical-host and genuine upgrade tests outstanding |
| PKG-02 | Build artifacts are repeatable under declared variations | Same-binary assembly and two fresh source/target builds compare binaries and complete archives with selected artifacts | Native CI gates and source-bound receipts; shared compiler/system environment, no independent-host or hermetic proof |
| PLT-01 | Platform reads preserve explicit identity and scope | Explicit endpoint/namespace/node, source versions, bounded collection and unknown/partial results; versioned source/profile contracts | Planned only; no Kubernetes or Talos adapter |
| PLT-02 | Platform credentials cannot expand read authority | Scoped permission manifest, verified TLS, explicit credential selection, no executable auth configuration or privileged fallback; exact-request and disclosure tests | Admission gate; not implemented |
| PLT-03 | Integrations preserve offline operation and data custody | Disabled/failing adapter leaves local CLI usable; no mandatory ecosystem tools or hosted control plane; deployment sovereignty and exit review | Planned; see [integration plan](platform-integrations.md) |
| REL-01 | Operational changes verify and recover | Approved writes verify preconditions/postconditions and provide rollback | Deferred; no operational write adapter in MVP |

Release gates also include exact-head Codex review and resolved discussions, required native CI/CodeQL, synchronized source/docs and post-merge identity/CI verification. Signed provenance, physical-host qualification and version-to-version package lifecycle remain additional gates before stable distribution.
