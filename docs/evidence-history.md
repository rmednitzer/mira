# Offline evidence comparison (experimental)

Capture `mira inspect --json > before.jsonl` and repeat later as `after.jsonl`. Compare with `.schema-venv/bin/python scripts/compare_evidence.py before.jsonl after.jsonl` after installing the pinned CI validator dependency. The command performs no host inspection, system mutation, network requests, persistence, or inference. It validates legacy JSONL against evidence-v1 and complete capture-v1, capture-v2 and capture-v3 documents against their local versioned contracts.

Limits: 1 MiB per capture and at most 128 unique source/scope records. Empty captures, duplicate JSON keys/source-scope pairs, malformed UTF-8/Unicode, nonfinite numbers, decimal/exponent numeric tokens, nesting beyond 32, unsupported versions and oversized inputs fail closed with exit code 2. Numeric fields use integer JSON tokens; even integral decimal/exponent forms are refused before any floating-point conversion. Exact large integers remain exact, and numeric-looking strings remain strings. This is a stricter admission rule than JSON Schema integer typing alone; current Rust producers already emit integer tokens. Output is deterministic JSON with sorted sources and no raw evidence values.

Outcomes: `changed` and `unchanged` apply only to two observed values for the same source and scope. `indeterminate` means at least one record is unavailable. `added` and `missing` indicate absence from one capture, **not** that a condition began or ended on the host.

All outcomes carry `freshness: unknown` and `clock_order: unverified`. Recorded wall-clock values are deliberately not used to assert chronology, freshness or trust, and collections are not atomic. Capture names (`before` and `after`) express caller intent, not a proven ordering. No authorization or remediation follows from a comparison.

[Complete captures](captures.md) add exact source coverage and an operator-asserted scope. Timeline captures (capture-v2, and capture-v3, which adds a consumer challenge) are admitted after timeline validation. Two of them produce comparison-v3, which adds same-boot order and interval from opt-in boot bindings; see [captures](captures.md#compare) and [ADR 0010](adr/0010-capture-timeline-and-freshness.md). Everything else here still applies: row outcomes and labels are unchanged. With `--allowed-signers FILE --principal NAME`, both captures must carry a valid `INPUT.sig`, verified over the bytes being compared, and the output gains an `integrity` member. With `--before-challenge`, `--after-challenge` and `--max-age-ms` as well, each capture must answer its own challenge and the output gains a `freshness` member with both age bounds; see [signatures](signatures.md). Matching complete formats/labels/profiles emit comparison-v2; mixed formats and mismatched scopes/profiles fail. A completion marker does not authenticate its producer. Legacy input has no completion guarantee. Input opens are nonblocking and the opened descriptor must identify a regular file; symlinks remain compatible and regular-file I/O has no general deadline.

The comparison is a small offline research utility rather than a persistent history store or a normalized diagnostic model. Package count changes are not package advisories or vulnerability determinations.
